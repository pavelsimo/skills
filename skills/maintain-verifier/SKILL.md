# maintain-verifier skill

A skill that does upkeep on a driver generated by `/create-verifier`. A feature map starts going stale as soon as the app changes. This pass finds where the map and the app disagree and fixes the map, never the app.

The unit of rigor is the feature, not every sentence. Every feature file is read against the source and every feature is driven live at least once. Not every bullet needs its own drive.

## features

- one read-only source reader per feature file, run in parallel, each returning drift with `file:line` citations and one live recipe
- sweeps commits since the last maintenance for user-facing surfaces the map is missing; a feature counts as missing only when a concrete source path backs it
- one live pass drives every feature, even when the source looks clean
- keeps three invariants for the whole pass: doctor before driving, evidence survives every cleanup, and nothing a drive started is left running
- triages each mismatch as doc drift, harness gap, product gap, or unreachable
- edits only `.skills/verify-<app>/`; product bugs are reported, never papered over in the map
- outcome is `clean`, `changed`, or `blocked`; `changed` ships as one commit of proven corrections

## usage

```
/maintain-verifier                  # maintain the only driver under .skills/verify-*/
/maintain-verifier <app>            # pick .skills/verify-<app>/ when there are several
/maintain-verifier --since <ref>    # sweep churn since <ref> instead of the last maintenance commit
```

## outcomes

Pick exactly one and name it in the report.

| Outcome | When |
|---------|------|
| `clean` | every feature got source and live coverage and nothing needed changing. No branch, no commit |
| `changed` | one commit ships proven corrections to the driver or the feature map |
| `blocked` | coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it |

A product bug in one feature does not make the pass `blocked`. Record it as a product gap and finish the rest.

## edit scope

- Edit only `.skills/verify-<app>/`: its `SKILL.md`, `features/`, and any helper scripts it owns.
- Never edit product code. If the map describes something the app no longer does, either the map is wrong (fix the map) or the app regressed (report it). Never rewrite the map to match broken behavior.
- Never delete anything under the evidence directory.

## workflow

1. **Locate the target.**
   ```bash
   ls -d .skills/verify-*/ 2>/dev/null
   ```
   - none: stop and point at `/create-verifier`; do not invent a target
   - several and no `<app>` given: ask which one
   - read `SKILL.md` and `features/README.md` in full before going further

2. **Index hygiene.** Compare `features/README.md` with the files in `features/` and fix entries that are:
   - missing: a feature file exists but the index does not list it
   - extra: the index lists a file that does not exist
   - duplicate: two files describe the same feature; merge them
   - dead: a link that points nowhere

   Keep this step quick. Do not build a generated inventory.

3. **Source wave.** Start one read-only reader per feature file, all at once, using the brief in [reference/source-reader.md](reference/source-reader.md). Readers never drive the app and never edit files. If the runtime cannot start sub-agents, do the same reads yourself, one feature at a time, and keep the same return shape.

4. **Reconcile.**
   - Every feature file needs a returned summary. Re-run any reader that came back empty.
   - Spot-check each cited drift by opening the cited `file:line`. Do not re-prove claims that came back clean.
   - Sweep recent churn for user-facing surfaces the map lacks:
     ```bash
     since="${SINCE:-$(git log -1 --format=%H -- .skills/verify-<app>/)}"
     git log --name-only --format='%h %s' "$since"..HEAD -- . ':!.skills'
     ```
     Look at changed routes, CLI commands, menus, and navigation. Call a feature missing only when you can name the source path that adds it. Add each missing feature as a new file in the same shape as the others; it gets driven in the live pass like the rest.
   - Merge overlapping recipes so the live pass needs as few app states as possible. Write down the drive order.

5. **Live pass.** Required even when the source looks clean. You do all the driving; readers never do. Use the driver's own Launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs and TUIs. Drive every feature at least once. Follow [reference/live-pass.md](reference/live-pass.md) for the invariants, doctor timing, the one-retry rule for doctor drift, and when a feature may be reported as `verified-unreachable`.

6. **Triage each mismatch.**

   | Kind | Meaning | Action |
   |------|---------|--------|
   | doc drift | the app works; the feature file describes it wrong or leaves out an entry point or prerequisite | fix the feature file |
   | harness gap | the app works; the driver cannot reach or observe it | fix the driver, then re-drive that feature live |
   | product gap | the app itself is broken | record it for the user; keep it out of the commit |
   | unreachable | a prerequisite the run cannot meet (auth, entitlement, OS, external service) | report with the prerequisite and the route attempted; if the map omits the prerequisite, that is also doc drift |

   Harness fixes follow the helpers rule from `create-verifier`: scripts are executable and their invocation is shown in the driver's `SKILL.md`.

7. **Final teardown.** Run the driver's Cleanup after the last drive of the run, including the re-drives from triage. Then confirm:
   - the evidence files exist at the location the driver names
   - nothing the run started is still running (for example `lsof -i :<port>` returns nothing)

8. **Ship or stop.**
   - `changed`: re-read every changed file, then create one branch and one commit with only files under `.skills/verify-<app>/`:
     ```bash
     git switch -c verify/<app>-maintenance-$(date +%Y%m%d)
     git add .skills/verify-<app>/
     git commit -m "✅ update verify-<app> driver and feature map"
     ```
     Ask before pushing or opening a pull request.
   - `clean` or `blocked`: no branch, no commit. Report the outcome and the coverage honestly.

9. **Report.**
   ```
   maintain: .skills/verify-<app>/
   outcome:  clean | changed | blocked
   since:    <ref swept for churn>

   index:    <fixed entries, or "ok">
   features: <feature> — ok | fixed (<doc drift / harness gap: what>) | unreachable (<prerequisite>, tried <route>)
   added:    <new feature files, with the source path that justified each, or "none">
   product:  <broken behavior the app showed, with evidence path, or "none">
   evidence: <paths from the live pass>
   commit:   <branch and sha, or "none">
   blocked:  <what stopped the pass, only for blocked>
   ```

Keep short run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in the run's evidence directory, which is gitignored. Never commit them.

## best practices

- **the feature is the unit** — cover every feature from source and drive every feature live; do not stop at the first convenient entry point when the map lists others
- **live even when clean** — a source read that finds no drift has not proven anything; the live pass is the proof
- **fix the map, never the app** — a regression goes in the report, not into a feature file rewritten to match it
- **doctor after surprises** — never drive an instance that has not been health-checked since it last did something unexpected
- **evidence outlives cleanup** — check that the files exist at the named location; do not assume it
- **re-drive every harness fix** — a driver change that was never driven live does not ship
- **one commit, proven** — every line in the commit was observed in the live pass; unproven guesses stay in the report
